# Спецификация требований (Lean Feature Spec)  
## Фича: Заселение гостя (Check-in)  

### 1. КОНТЕКСТ (User Story)  
**Как** администратор стойки регистрации, **я хочу** быстро оформлять заселение гостя в систему с автоматической проверкой статуса номера и брони, **чтобы** минимизировать время ожидания гостя и исключить ошибки заселения в грязные или занятые номера.

### 2. СПИСОК ФУНКЦИОНАЛЬНЫХ ТРЕБОВАНИЙ (FR)  
*   **FR1:** Система должна находить активную бронь по фамилии гостя или номеру брони.  
*   **FR2:** Система должна отображать список только тех свободных номеров, статус которых — «Свободен» (Чистый).  
*   **FR3:** Система должна блокировать процедуру заселения, если номер имеет статус «Грязный» или «На ремонте».    
*   **FR4:** Система должна создавать новую запись о бронировании, если гость заселяется без предварительной брони.  
*   **FR5:** Система должна изменять статус номера на «Занят» сразу после успешного завершения процедуры Check-in.  

### 3. СЦЕНАРИЙ (Use Case) - Детализация  
**Название:** Оформить заселение гостя (Check-in).  
**Актор:** Администратор.  
**Предусловия:** Администратор авторизован в системе. Гость находится на стойке регистрации.  
**Постусловия (Успех):** Создана запись о проживании, номер переведен в статус «Занят», гость получил ключ.  
**Постусловия (Неудача):** Процесс прерван, статус номера не изменен, гостю выдано сообщение об ошибке.

**Основной поток (Happy Path):**  
1. Администратор запрашивает у гостя документ.  
2. Администратор инициирует поиск брони в системе (по ФИО или номеру брони).  
3. Система отображает данные брони.  
4. Администратор подтверждает заселение и вводит паспортные данные (если их нет в картотеке).  
5. Система проверяет статус закрепленного номера (должен быть «Свободен»).  
6. Администратор принимает оплату (если не была предоплата).  
7. Система фиксирует оплату, меняет статус номера на «Занят» и создает запись о проживании (Stay).  
8. Администратор выдает гостю ключ.

**Альтернативные потоки:**  
*   **2а. Бронь не найдена:** Администратор переходит к поиску свободных номеров на текущую дату. Если номера есть — оформляет новую бронь (FR4) и продолжает с шага 4. Если нет — отказ в заселении.  
*   **5а. Номер «Грязный» или «На ремонте»:** Система блокирует заселение (FR3) и предлагает администратору выбрать другой доступный номер. Если гость согласен — процесс возвращается к шагу 4. Если нет — процесс завершается.

### 4. КРИТЕРИИ ПРИЕМКИ (Acceptance Criteria)  
*   **AC-1 (Проверяет FR2):**   
    *   *Given:* В отеле есть номер 101 (статус «Свободен») и номер 102 (статус «Грязный»).  
    *   *When:* Администратор открывает список доступных номеров для заселения.  
    *   *Then:* В списке отображается только номер 101.  
*   **AC-2 (Проверяет FR3):**  
    *   *Given:* Гость с активной бронью на номер 102. Статус номера 102 — «Грязный».  
    *   *When:* Администратор пытается заселить гостя в номер 102.  
    *   *Then:* Система выводит сообщение: «Заселение невозможно: номер не убран» и блокирует кнопку «Заселить».  
*   **AC-3 (Проверяет FR5):**    
    *   *Given:* Администратор успешно завершил оформление заселения в номер 101.  
    *   *When:* Процесс завершен.  
    *   *Then:* Статус номера 101 в «Шахматке» меняется на «Занят» (цвет меняется на красный).  

### 5. СПИСОК НЕФУНКЦИОНАЛЬНЫХ ТРЕБОВАНИЙ (NFR)  
*   **NFR-1:** Поиск активной брони по фамилии должен занимать не более 1 секунды (при базе до 10 000 записей).  
*   **NFR-2:** Интерфейс заселения должен корректно работать в браузерах Chrome и Firefox последних версий (ограничение локальной сети отеля).
